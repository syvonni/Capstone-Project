# Comprehensive Application Audit Logging Megaplan

Replace the ad-hoc, minimal application audit calls with a single `ApplicationAuditHelper` that records *who* did *what* to *which application*, with change summaries and request context, and wire the audit event taxonomy / service config / frontend audit cards so Application History shows named entities, performed-by, and decision context instead of "Unknown Entity".

## 1. Objective

- Enrich every application lifecycle audit log with the same quality of metadata as the variable audit trail (`userName`, `userEmail`, `name`, `applicationReferenceNumber`, `ip`, `method`, `path`, `changedFields`, `changeCount`, `changeSummary`, `oldStatus`/`newStatus`, `decision`, `comments`, `rejectionReason`, `fieldKey`, `fieldDecision`, `returnCount`).
- Stop emitting duplicate / overlapping application events (`application_reviewed` vs `pending_action_executed` vs `application_approved`/`rejected`/`returned`).
- Ensure `GET /api/audit/application/:id` returns *all* relevant events, including `field_reviewed`, `field_decisions_updated`, and `pending_action_*`.
- Update the frontend `DefaultAuditCard` / `AuditEventDetails` (or create application-specific components) so cards show the business name and performer, and details show the change summary and decision context.
- Preserve the existing workflow and approval/pending-action behavior; this is only about audit metadata, not business logic.

## 2. What you already told me

| Question | Your answer | Plan consequence |
|----------|-------------|------------------|
| Scope | **Applications only** | We refactor only `Application` / `Business` lifecycle events. The helper may be reusable later, but the implementation and rollout are scoped to the application/permit flow. |
| Backfill | **New logs only** | We do not touch existing audit records. Old logs will still show "Unknown Entity" until they age out. A follow-up backfill script can be added later if you change your mind. |
| Snapshots | *"I’m not sure, also record field decisions."* | **Recommendation: key fields + diffs, never full application snapshots.** Full `formData` JSON is large, contains PII, and would bloat the audit collection. We record `changedFields`, `changeCount`, `changeSummary`, `oldStatus`, `newStatus`, and field-level diffs only. |
| Event taxonomy | *"I’m not sure, but pending action events should be recorded."* | **Recommendation: standardize lifecycle, keep pending-action events, and drop `application_reviewed`.** `pending_action_executed` is the canonical final-decision event. Direct review endpoints will emit `application_approved` / `rejected` / `returned` instead. |

### Devil’s advocate on snapshots
Application `formData` can include addresses, tax certificate numbers, document CIDs, and eventually uploaded file references. Storing complete `oldSnapshot` / `newSnapshot` like variables do would:
- create multi-MB audit documents,
- duplicate PII and document CIDs into the audit trail,
- make change summaries noisy (a single resubmit changes many fields at once).
Variables are small config records; applications are not. The variable pattern should be **adapted**, not copied verbatim.

## 3. Acceptance criteria

1. `GET /api/audit/application/:id` returns a coherent timeline: `created` → `submitted`/`resubmitted` → `claimed` → `review in progress` → `pending_action_created` → `pending_action_executed` → `returned`/`approved`/`rejected`.
2. Every returned log has `metadata.name` (business name), `metadata.userName`, `metadata.userEmail`, `metadata.applicationId`, `metadata.applicationReferenceNumber`.
3. `DefaultAuditCard` no longer shows "Unknown Entity" for application events; it shows the business name and "Performed By".
4. `AuditEventDetails` shows a human-readable `changeSummary` and key fields for status/return/reject/approve/field-review events.
5. Application Progress continues to render the same timeline, with richer dates/names.
6. `npx eslint` on touched backend and frontend files passes; `npm run build` in `web/` passes; backend tests in scope still pass.
7. New logs do **not** contain full `formData` snapshots.

## 5. Current state analysis

### Backend audit calls are minimal and inconsistent
- `application.service.js` logs `application_created`, `application_autosaved`, `application_updated`, `application_submitted`, `application_claimed`, `application_approved`, `application_rejected`, `application_returned`, `application_email_resent`, `application_deleted`.
- `permitApplication.service.js` logs `application_reviewed`, `application_claimed`, `application_released`, `application_status_reset`, `field_reviewed`, `field_decisions_updated`, `officer_draft_deleted`, `email_resent`, `email_status_reset`.
- `pendingAction.service.js` logs `pending_action_created`, `pending_action_cancelled`, `pending_action_executed`.
- `walkInApplication.service.js` logs `walkin_application_created`, `officer_draft_finished`.
- None of these set `metadata.name`, `metadata.userName`, `metadata.userEmail`, `metadata.ip`, `metadata.method`, `metadata.path`, or `changedFields`.

### Event taxonomy is incomplete in the audit service
- `audit-service/src/config/auditEventTypes.js` `applications` array is missing `application_created`, `application_updated`, `application_autosaved`, `application_deleted`, `application_email_resent`, `application_reviewed`, `application_resubmitted`, `pending_action_executed`, `field_reviewed`, `field_decisions_updated`.
- `pending_actions` and `field_reviews` are separate categories, but `entityAuditConfig.application` only consumes the `applications` array, so `GET /api/audit/application/:id` currently filters out field-review and pending-action events even though they carry `metadata.applicationId`.

### Frontend cards rely on metadata the application logs do not provide
- `DefaultAuditCard` title = `metadata.name || 'Unknown Entity'`.
- "Performed By" only appears if `metadata.userName || metadata.updatedByName || ...` exists.
- `AuditEventDetails` priority list is `eventType`, `name`, `createdAt`, `userName`, `changedFields`, `changeCount`, `changeSummary`, `version`.
- Application logs have none of these, so the card is blank and the detail panel only shows a raw JSON blob.

### The variable pattern already exists and is reusable
- `VariableAuditHelper` + `AuditMetadataBuilder` + `trackChanges` already build rich metadata.
- `getUserInfo(userId)` already resolves user name/email.
- We can build the same pattern for applications, but with a lighter diff strategy because `formData` is large and nested.

## 6. Proposed design

### 6.1 New helper: `ApplicationAuditHelper`

Create `backend/services/business-service/src/lib/auditHelpers/applicationAuditHelper.js` as a static-method class.

It imports:
- `logAuditEvent` from `../auditClient`
- `AuditMetadataBuilder` from `../auditMetadataBuilder`
- `getUserInfo` from `../../../../../shared/lib/getUserInfo`
- a new `diffApplication(oldApp, newApp)` helper for status/formData changes

Public methods (one per lifecycle event):

```
logCreated(req, userId, application, role)
logWalkInCreated(req, officerId, application, role)
logOfficerDraftFinished(req, officerId, application, role)
logAutosaved(req, userId, application, role, changedFields)
logSubmitted(req, userId, application, role, { isResubmit, oldApplication })
logUpdated(req, userId, application, oldApplication, newApplication, role)
logClaimed(req, officerId, application, role)
logReleased(req, officerId, application, role)
logTransferred(req, officerId, application, newOfficerId, role)
logFieldReviewed(req, officerId, application, fieldKey, decision, reasonCode, reasonOther)
logFieldDecisionsUpdated(req, officerId, application, decisions, oldDecisions)
logPendingActionCreated(req, officerId, application, actionType, scheduledAt, payload)
logPendingActionCancelled(req, officerId, application, actionType)
logPendingActionExecuted(req, officerId, application, actionType, newStatus, payload)
logApproved(req, officerId, application, comments, oldApplication)
logRejected(req, officerId, application, comments, rejectionReason, oldApplication)
logReturned(req, officerId, application, comments, oldApplication)
logStatusReset(req, officerId, application, newStatus, oldApplication)
logDeleted(req, userId, application, role)
logEmailResent(req, officerId, application, emailType)
logEmailStatusReset(req, officerId, application, emailType)
```

Each method:
1. Calls `getUserInfo(userId)` to get `{ name, email }`.
2. Calls `new AuditMetadataBuilder(req)` and chains:
   - `.withUserInfo(userInfo)` → adds `userName`, `userEmail`, `userId`
   - `.withRequestInfo()` → adds `ip`, `method`, `path`
   - `.withEntityFields(application, { name: 'businessName', applicationId: 'applicationId', applicationReferenceNumber: 'applicationReferenceNumber' })` → adds `name`, `applicationId`, `applicationReferenceNumber`
   - `.withCustomFields({ ... })` for event-specific context
3. Calls `logAuditEvent(eventType, userId, 'application', application.applicationId, metadata)`.

### 6.2 Application diff strategy

For `logUpdated`, `logSubmitted` (resubmit), `logApproved`, `logRejected`, `logReturned`, `logStatusReset`:

- Capture `oldApplication` before the mutation (`oldApplication = application.toObject()` or a clone before save).
- After save, compare selected top-level fields: `applicationStatus`, `businessName`, `reviewComments`, `rejectionReason`, `reviewedAt`, `reviewedBy`, `returnCount`, `returnExhausted`.
- Compare top-level `formData` keys: collect keys whose values changed (stringified). Do **not** store full formData values; store only the key names and, for a small allow-list of non-sensitive scalar fields (e.g. `businessName`), the old/new values.
- Build `changedFields`, `changeCount`, `changeSummary`.
- Add `oldStatus` / `newStatus` for status transitions.
- Example `changeSummary`: `"applicationStatus: resubmit -> returned; reviewComments: added; formData: businessName, locationOfActivity changed"`.

### 6.5 Service / controller changes

The helper needs:
- `req` (for IP/path; optional, safe if missing)
- `userId` / `officerId`
- `application` (old and new, when applicable)
- role string

To pass these without breaking tests, add an optional `auditContext` object as the **last** argument to mutating service methods:

```js
// service
async submit(id, userId, auditContext = {}) {
  const { req } = auditContext;
  ...
}

// controller
return await this.service.submit(req.params.id, req._userId, { req });
```

Affected methods (each needs a one-line controller change):
- `ApplicationService`: `create`, `patchFormData`, `update`, `submit`, `claim`, `approve`, `reject`, `returnForRevision`, `resendEmail`, `delete`
- `PermitApplicationService`: `startReview`, `claimApplication`, `releaseApplication`, `reviewApplication`, `resetApplicationStatus`, `updateFieldDecisions`, `deleteApplication`, `resendEmail`, `resetEmailStatus`
- `PendingActionService`: `createPendingAction`, `cancelPendingAction`, `executePendingAction`
- `WalkInApplicationService`: `createWalkInApplication`, `finishWalkInApplication`

Controllers currently call `this.service.xxx(...)`; we add `{ req }` as the last argument.

The helper calls `logAuditEvent(...).catch(...)` so audit failures never block the request.

### 6.7 Redaction / sensitive data rules

The helper must NOT store:
- Full `formData` JSON in snapshots.
- Document CID values or file URLs.
- Tax certificate numbers, registered addresses, or other PII in change summaries.

It MAY store:
- Top-level formData keys that changed.
- `businessName` old/new values.
- Status, review comments, rejection reasons, field decisions, and officer names.

## 9. Risks and considerations

- **Service signature drift**: Adding `{ req }` to many methods is mechanical but easy to miss. We can make the helper tolerate a missing context to keep unit tests that call services directly working.
- **Performance**: `getUserInfo` adds a DB lookup per audit event. Since audit is fire-and-forget, this should not block the request, but it adds load. We can cache by `userId` for a single request or accept the small overhead.
- **Audit document size**: Even with diffs, many formData changes could make `changedFields` large. We can cap `changeSummary` length at 500 characters and `changedFields` at 50 entries.
- **Old logs**: Because we are not backfilling, old logs will still show "Unknown Entity". This is accepted per your answer.
- **Event ordering**: `pending_action_executed` and `application_approved` could duplicate if both are logged. We will ensure the direct `reviewApplication` endpoint emits only the appropriate lifecycle event, not a generic `application_reviewed`.
- **Variable audit helpers already use `getUserInfo` with a hard cross-service import path** (`shared/lib/getUserInfo` → `business-service/src/models/User`). We should verify this works in Docker; if not, we may need to pass `userInfo` from the controller or use the `User` model directly.
